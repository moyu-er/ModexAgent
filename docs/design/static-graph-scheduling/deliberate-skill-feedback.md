# deliberate skill 使用反馈

> 来源：实际使用 /deliberate 讨论 ticket 01-03 时的行为问题
> 日期：2026-08-07

## 问题 1：讨论结论只写文档，不在对话末尾提出

**现象**：每次讨论后，把结论更新到 ticket md 文件，然后简短说"已更新，你看还有要调整的吗"，核心问题没有在对话中明确提出。

**期望**：讨论结论写文档**同时**，在对话末尾把待确认的核心问题/建议**直接提出来**，让用户在对话中就能看到并回应，不需要打开文件自己找。

**修正**：文档记录 + 对话末尾明确提出问题是两件事，都要做。对话末尾的提出是主要交互面，文档是持久化记录。

## 问题 2：过早跳到实现细节

**现象**：03 讨论时，用户给了整体视角（"图调度是独立于会话/pool 的系统"），我立刻跳到"graph 作为 execution strategy"的具体实现方案（GraphStrategy.assemble 做什么、GraphSpec 存哪）。

**期望**：先用整体视角对齐定位，确认方向后再深入细节。用户说"这个太细节了"是信号——退回整体层面。

## 问题 3：理解偏差后修正不够主动

**现象**：多次出现理解偏差（state 作为数据总线、mid-execution 概念、kb 现状），用户纠正后我修正但有时不够彻底，残留的旧理解还会影响后续讨论。

**期望**：纠正后主动重新审视之前的结论是否还成立，明确哪些需要跟着改。

## 问题 4：探索不够就下结论

**现象**：01 讨论时基于 ADR 描述下结论，没有先读实际代码。用户指出"你要看看当前 src/modex_graph/ 的设计、实现"后才补做探索。

**期望**：deliberate skill 的"investigate before replying"原则——先探索代码确认事实，再给倾向。
