# 17 — Multi-workspace parallel + WebUI workspace creation

**What to build:** Multiple workspaces run in parallel with structural isolation, and the WebUI can create a new workspace at runtime: create → assemble from the default/hosted declaration → usable immediately (its pools boot on the declaration path). Parallel execution is the first-class target — not just `/cd` switching: concurrent turns in different workspaces must not cross-talk (tool root providers, memory, transcripts all per-workspace by the four-layer isolation invariants). Dynamic creation writes the declaration back to disk (survives restart). This ticket delivers the user's explicit concern: parallel multi-workspace execution and WebUI-created workspaces on the same logic as switched ones.

## Resolution notes

- **Creation road** (`bot/workspace/dynamic_workspaces.py`): `create_workspace(service, name=, backend=)` writes `config/scopes/workspaces/<name>.yml` — a full loadable declaration (the primary's hosted pools copied verbatim at YAML level — model-equality asserted — with the workspace layer reduced to name + optional persistence backend) — then materializes through `ScopeRegistry.materialize` (the SAME lazy-materialization road a `/cd` target takes; no hot assembly, N2). Materialization runs BEFORE the registration upsert so a failed creation rolls back declaration + empty root with no ghost registry context.
- **Name→root identity**: a dynamic workspace's root is deterministic — `<project>/subworkspace/<name>` (the existing runtime-populated workspace convention). `dynamic_workspace_declaration_path(project_dir, target)` routes a materialization at that root to its declaration file; every other target (home, arbitrary `/cd` paths) keeps booting `bot.yml`.
- **Restart persistence**: `register_dynamic_workspaces(service)` runs at `BotService.initialize` — it reads `workspaces/*.yml` through the new FW loader `load_dynamic_workspace_declarations` (`modex_agent/scope/loader.py`, the one sanctioned directory read — identity = file stem, enforced loudly) and registers each root via `get_or_open`. Lazy materialization on the first targeting turn reassembles it the same way; the registry store is merely a cache.
- **Per-workspace resource selection**: `_assemble_resources` re-applies `apply_workspace_resource_selection` per materialization — idempotent for the primary declaration, effective for a dynamic workspace's backend override. A per-workspace `paths` override is refused loudly (the WorkspaceContext is built with the service-level layout — a differing data_dir_name would silently split stores; only reachable by hand-editing a declaration).
- **WebUI surface**: `POST /api/workspace/create` (`routes/workspace.py`, following the `/api/workspace/cd` precedent; 503 unwired / 400 validation / 409 collision / 500 boot failure) wired via `WebUIServer.set_workspace_creator` in `WebUIService`. Frontend: a minimal create section in `WorkspaceBrowser` (name input + backend select + Create → switch to the returned path, same as a picked folder).
- **Tests** (`tests/integration/test_workspace_runtime_parallel.py` — real `BotService`, only the LLM scripted): (a) full chain (declaration loadable + pools booted + bridges running + echo turn through the real dispatcher, zero restart); (b) concurrency proven by a barrier in the scripted LLM — each turn's first round blocks until BOTH turns are in flight (serialized execution deadlocks and times out); four probes: real `write` tool relative-path writes (root provider ②), real memory read-back through each workspace's own memory system (①), and the real ctxvar-routed `WorkspaceScopedTranscriptStore`/`WorkspaceScopedMediaStore` writes from inside each turn (③) — zero cross-references; (c) `max_materialized` unset + both workspaces remain materialized; (d) existing `/cd`/switch tests unchanged and green; (e) full stop + registry-store wipe + re-boot → the declaration alone re-registers and equivalently reassembles the workspace (chat works again); (f) two conversations through one input adapter route to their own workspaces with replies on their own session ids.
- **Known pre-existing (not this ticket)**: 4 failures in `examples/bot_project/tests/integration/test_peer_pool_assembly.py` — fail identically at the parent commit under full PYTHONPATH isolation (legacy `config/pools` fixtures never migrated for the bot-side integration run, which is not part of any plan gate).
