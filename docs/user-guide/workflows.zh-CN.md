# 工作流

本指南从选择工作区开始，按用户可见的操作走到经过核验的结果。其中的 WebUI 名称与随附参考应用中的实际文案一致。

## 选择工作区、Pool 和会话

工作区是文件、运行状态、Pool 和记忆的项目边界。Pool 决定该会话的根 agent，以及它可以使用的协作者。会话则把后续轮次和可能产生的子 agent 会话组织在一起。

1. 在工作区标签栏使用 `Open workspace`。
2. 选择最近目录、浏览到目标目录，或用 `Create Workspace` 创建隔离工作区。
3. 如果存在多个 Pool，在左侧栏选择 `Agent pool`。
4. 点击 `New Conversation`，然后发送第一条消息。

新会话创建时会固定到当时选中的 Pool。切换侧栏中的 Pool 只会筛选会话列表，不会把已有会话迁移到另一个 Pool。新任务依赖已有上下文时回到原会话；彼此独立的任务则新开会话。

## 提交可闭环任务

有效请求应明确结果、边界、验证方式和期望报告。模型可能自己完成，也可能使用可用协作者；不能保证它一定委派。

### 编码任务

选择具备编码能力的 Pool，并明确完成条件：

```text
修复 CSV 导出在字段含换行时失败的问题。
先复现，再做最小且正确的修改。
运行针对性测试，并报告修改文件、测试命令和结果。
不要改动无关格式或配置。
```

检查最终回答是否同时包含诊断、修改、验证和剩余风险。如果结果不完整，在同一会话中补充缺少的检查，不必重新描述整个任务。

### 只读调研任务

如果任务不能改动工作区，请选择具备合适只读能力的 Pool：

```text
研究一条 WebUI 消息如何到达所选 Pool。
不要编辑文件，也不要运行会改变状态的命令。
返回调用路径、关键决策和准确文件引用。
把不确定项与已核实事实分开列出。
```

提示词只能表达意图，不能代替权限控制。如果必须只读，请确认所选 agent 的工具集和 sandbox 策略配置。你可以要求根 agent 在适合时使用只读调研协作者，但模型也可能合理地选择其他有效路径。

## 跟进任务执行

### 会话树

左侧 `Conversations` 会把根会话与发现的子会话显示成树。展开父节点并选择子节点，即可检查该子 agent 的会话记录。子会话显示为 `Read only`，因此后续任务应从根会话继续。

只有运行中的 agent 确实创建了子会话，树中才会出现对应节点。没有子节点时，可能是根 agent 自己处理了任务；仅凭缺少子节点不能判定请求失败。新发现的各级子会话会关联到对应父会话，包括 OpenCode 报告的子会话。

### 工具调用记录

工具调用会以内联可折叠卡片显示，卡片名称就是工具名。展开卡片可以检查 `Args` 和 `Result`；完成的调用带有 `done` 标记。应通过调用记录核实读取、修改和执行动作，而不是只根据文字描述推测。

工具成功不等于任务成功。编码任务还要检查最终总结和报告的测试结果。调研任务则要确认结论有证据，并且没有使用写入工具。

## 暂停与审批

### 暂停当前轮次

会话正在响应时，`Pause` 会取消当前轮次。它不会删除会话，之后仍可发送纠正信息或范围更小的后续请求。它也不会回滚已经完成的命令或文件写入；重试前应检查工作区。

会话中的 `Pause` 与下文图实例的 `Pause` 不同。前者结束当前 agent 轮次，后者保留图实例以便 `Resume`。

### 处理审批请求

只有原生 agent 启用了审批，且工具调用需要决策时，才会出现审批卡片。选择 `Approve` 前先阅读工具名、风险级别和参数。
只有每个待处理调用都符合预期时才使用 `Approve All`。`Deny All` 会拒绝整批；拒绝任意一张待处理卡也会取消整批。

审批是可配置能力，不代表每次工具调用都必然暂停。OpenCode 的外部工具不经过框架的原生工具审批流程。

## 运行图工作流

图工作流是工作区级 YAML 规格，在 `Graphs` 中显示。它负责协调节点并持久化图实例生命周期，但并不等同于聊天会话。

### 使用临时工作区

Agent 节点可以在所选工作区中编辑文件和运行命令。尝试编码图工作流前，先准备包含图配置的临时克隆、一次性副本或专用 Git worktree，并将其作为工作区打开。
启动前确认标签页中的工作区路径，结束后检查其 diff。这样测试 `Pause`、`Deliver` 或循环工作流时不会破坏真实工作树。

图内的原生 Agent 轮次会保留已配置的防护，但不会弹出人工工具审批卡片。运行工作流前应检查策略，不要依赖聊天中的审批设置让图在执行时停下来请求确认。

### 理解 `review_cycle`

随附的 [`review_cycle.yml`](../../examples/bot_project/config/graphs/review_cycle.yml) 把 `coder` 连接到 `reviewer`。`coder` 节点实现请求，并向 `reviewer` 交付修改总结。
`reviewer` 被要求检查实际 diff 和验证结果。它可以把具体修改意见交回 `coder`，也可以把已接受结果交付到图工作流终点。

这是循环工作流，因此应提供有边界、可测试的请求，并留意节点是否重复活动。需要深入实现时，可阅读节点到 agent 的桥接实现 [`agent_node.py`](../../examples/bot_project/bot/graph/agent_node.py)。

### 创建并检查图实例

1. 打开 `Graphs`，选择 `review_cycle` 图工作流规格。
2. 点击标记为 `New Instance` 的加号按钮。
3. 输入初始请求并点击 `Run`。
4. 打开实例行，查看状态、进度、输入和输出。
5. 点击 `Topology` 打开实时拓扑视图。
6. 使用侧栏中标记为 `Events` 的区域查看事件时间线。

选择节点可查看它的状态、调用记录和结果。Agent 节点已有会话时，可用 `Open session transcript` 跳转到对应会话记录。

### 控制运行中的图实例

`Pause` 会请求 pending 或 running 图实例停止调度新工作，并收敛到 `paused`。状态变为 `paused` 后，用 `Resume` 继续同一个图实例。
图实例不应继续时，使用 `Stop` 将其结束；已 stopped 的图实例不会恢复。

图实例处于 `running` 或 `paused` 时，会显示 `Deliver to node`。选择 `Node`、输入内容，再点击 `Deliver`，即可向该节点注入工作。
这是操作员控制，不是普通聊天回复，可能改变后续可运行的工作。

### 图实例与 Agent 会话的关系

图实例保存拓扑、节点状态、事件、输入和最终输出。每个 agent 节点都通过一个 agent 会话运行，模型输出与工具调用记录保存在该会话中。
节点会话还可以拥有子会话，它们仍会出现在普通会话树中。图实例的 `Pause` 会协调活跃节点的会话树，使同一个图实例之后可以恢复。

### 编辑图工作流

打开图工作流规格，然后点击 `Edit YAML`。在 `YAML Configuration` 中编辑文本，检查拓扑预览，再点击 `Save`。
YAML 中会显示解析或验证错误；修复后再运行新实例。

拓扑只是预览，不是可视化图编辑器。
拖动画布只会平移视图，滚动只会缩放；节点和边通过 YAML 修改，不支持 drag-and-drop 编排。

## 使用内置 OpenCode 集成

ModexAgent 内置了与 OpenCode 外部编码 agent 的集成；满足前置条件时，它会作为可选 Pool 出现。

### 准备 OpenCode

1. 单独安装 `opencode` CLI，并确保 ModexBot 进程继承的 `PATH` 能找到它。
2. 使用 OpenCode 自身配置设置 provider 凭据和模型。
3. 选择 `opencode` Pool 前，先确认 CLI 能在目标工作区中运行。
4. 修改进程级 `PATH` 或 Pool 声明后重启应用。

如果启动时找不到可执行文件，OpenCode Pool 会被跳过，其他 Pool 仍可使用。
不要把 provider secret 写进工作流提示词或提交的图工作流 YAML。

### 运行职责

WebUI 是共享工作台，用于选择工作区和会话，以及查看流式输出。
对于 `opencode` Pool，OpenCode 负责其原生会话、生成输出、模型选择、工具执行、上下文和权限行为。
ModexAgent 负责映射外部会话、把事件路由到共享会话记录，并可显示发现的子会话。

不能假设 ModexAgent 原生的 MCP 分配、Skills、sandbox 元数据和审批设置会约束 OpenCode 自己的工具。
如需等价控制，应在 OpenCode 侧配置，并把 OpenCode 的权限视为实际边界。
更深入的集成细节见[外部 coding-agent 设计](../design/external-coding-agent-integration/spec.md)。

### 执行并核验

点击 `New Conversation` 前先选择 `opencode` Pool，再按上文相同的闭环格式发送任务。
在共享会话记录中跟进文本、reasoning 和工具卡片；如果 OpenCode 创建了子会话，再检查会话树。
当前轮次应停止时使用 `Pause`，但要检查工作区，因为已完成的外部工具动作不会回滚。
最后检查真实 diff 或产物，以及报告的验证命令。

## 通过 QQ 或 Telegram 接入

QQ 和 Telegram 是访问已配置 Pool 的其他渠道，并不定义另一套 agent 运行流程。
渠道设置、凭据和渠道专用控制统一见[配置](configuration.zh-CN.md)。
任务闭环保持一致：确认目标工作区和 Pool，说明结果与检查项，观察运行过程，再核验产物。

## 完成检查清单

- 当前工作区和固定的 Pool 都符合预期。
- 最终产物或答案满足请求，而不只是最后一个工具成功。
- 工具调用记录和子会话能支持所声称的工作。
- 要求的测试或只读约束已经实际核验。
- 待审批项已处理，且没有会话或图实例意外保持活跃。
- 编码实验在临时工作区中运行，产生的 diff 已检查。
