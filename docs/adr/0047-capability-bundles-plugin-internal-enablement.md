# Capability Bundles — Plugin-Internal Enablement and Derivation

## Context

ADR-0041/0042 made single components registerable (10 slots) and agent composition declarative (scope tree), but capabilities that ship as a set — a tool plus its hook plus its prompt guidance plus its pool store — still bind through five coexisting mechanisms: compiler hard-coded tree derivation (`_derived_entries` for the communication trio), compiler special cases (the experience name-merge and hook injection), a closed `ToolSupplement` enum, assembly-time unconditional injection with runtime tool-registration gates (todo hooks, todo/communication prompt providers), and position-derived defaults. A third-party author of a bundled capability can only register loose components and ask users to name each one; the bundle's internal binding is inexpressible. The user further required: derivation (including `task`) lives inside the plugin, not the compiler; plugins may scan the declaration to decide their own enablement dynamically; and all remaining glue that hard-codes configuration is unacceptable — everything reaching an agent must be configuration-resolved.

## Decision

**A Capability is the 11th component slot — the cross-slot bundle unit, and the ownership unit for an optional feature.** One plugin unit declares an enablement predicate, compile-time contributions (tool names, tool replacements, hook names, prompt sections), a pool-level supply, and per-agent wiring — and owns the feature's **implementation** (models, sources, curators, reviewers, prompts, config): a full vertical slice, not assembly glue. A Capability that only wired the slots while its implementation stayed scattered across `core/`, `agents/`, `memory/`, and `hook/` would split the semantic owner from the runtime owner; that shape was explicitly rejected (migration plan §7.4). A bundle is enabled per agent via the `capabilities:` declaration map. Contributed names flow into the existing tool/hook rosters and resolve through the existing TOOL/HOOK slots — no second resolution path. Five bundled capabilities migrated onto it (`ast_grep`, `aci`, `todo`, `experience`, `subagents`), later joined by the Experience and Skills feature packages (below); `ToolSupplement`, the `tool_supplements` field, and the compiler special cases die.

**Settled feature ownerships (architecture-convergence migration, `ARCHITECTURE-MIGRATION-PLAN.md` §10–§11).** Experience is a full vertical slice under `plugins/defaults/capabilities/experience/`: capability, supply, config, models, catalog, source, metadata, validation, curator, reviewer, review hook, tools, tool/hook factories, section, paths, and prompts in one package; its supply is the single lifecycle owner (curator and review tasks start, stop, and are awaited at teardown; capability config is the only config source). Skills is a runtime vertical slice under `plugins/defaults/capabilities/skills/`: capability, supply, models, source, catalog, cache, filter, builder, and section, with `SkillsSupply` owning the per-agent `SkillCatalog` mapping (one catalog per native agent, main and subagent built through the same path). Neither is a top-level mandatory subsystem: their enablement and lifecycle are capability-owned, which is exactly why `modex_agent.skills` / `modex_agent.experience` packages were rejected (migration plan §7.2). Each feature registers through one package-owned `register_experience_feature(ctx)` / `register_skills_feature(ctx)` entry; generic callers see only the normal slots (`Capability`, `CapabilitySupply`, `SystemPromptProvider`, `Tool`, `Hook`), and the package facades are import-light (importing one must not eagerly import reviewer, memory, tool, or hook implementation modules).

**Skills settled semantics.** Assignment authority is disk at `skills/<pool>/<agent>/`, optionally augmented per agent by `capabilities: {skills: {roots: [...]}}`; scope declarations do NOT enumerate individual skills. Enablement is automatic for native agents (absent roots yield an empty catalog — wiring stays), and `capabilities: {skills: false}` remains the explicit per-agent veto. `SKILL.md` frontmatter is parsed into structured metadata while `Skill.content` is always the body after the closing fence. `disable-model-invocation: true` removes every trace of that skill from the system prompt but leaves the complete catalog available to explicit slash invocation. Both command onramps — the Bot Input Pipeline (`SkillParseStage`) and direct `AgentPipeline` invocation (`SkillCommandHandler`) — are legitimate inbound adapters that call exactly one `SkillResolver.resolve_command()`; their canonical XML contains body only, never frontmatter. The `SkillResolver` interface is consumer-owned and lives in `commands/skill.py`, not in the Capability package: lower-level `commands` and the Bot Input Pipeline never import `plugins`, and the Skills package never imports `multi_agent` (dependency direction `multi_agent -> bundled capability -> commands/core`).

**Enablement resolution: effective set = auto-apply ∆ declaration override, and the judgment is the capability's own.** Each capability declares `applies(declaration_view) -> bool` (default False — pure opt-in), a pure function over the agent's declaration state: tree position (children/parent/peers/is-root) plus its own declared fields. It never reads the final roster or other capabilities' contributions (enablement circularity would break spec-hash determinism). The `capabilities:` field is an **override map** — `false` forces a capability off, a config mapping forces it on with config; explicit override wins over the auto face in both directions. The field is never a whole-set declaration; the scope bill (three-state entries: auto / declared / vetoed) is the only authority on what an agent effectively has. External agents are structurally excluded before resolution, so an auto-applied capability can never leak into the external plane.

**Derivation lives in the plugin; the framework defaults to an empty capability set.** `contribute(tree, config)` runs before roster merge (so `tools:/hooks:` ± stays the component-level veto), `bind(tree, config, final)` runs after it (anchor checks — e.g. an agent with declared children whose final roster lost `task` is a boot failure with repair guidance). The compiler knows no capability name: `subagents`' auto-apply predicate (`bool(children) or not is_root or bool(peers)`) preserves today's zero-config communication behavior without the framework hard-coding a default set — an earlier draft's framework-level default `[subagents]` was rejected precisely because it made the framework name a capability.

**Two veto altitudes, one syntax each.** Capability-level: the override map's `false` (the package does not compile in). Component-level: the existing `tools:/hooks:` ± merge on the contributed roster entries. No `[-capability]` list syntax — capabilities are a map, not a list.

**No-declaration-face injection dies as an invariant.** Every component reaching an agent must be traceable in the compile product (local declaration / profile / position default / capability contribution, auto-applied or declared); assembly code that unconditionally injects a component is a defect. The remaining code-wired defaults (`deliver_retry`, `length_guard`, `model_choice_bind`, `native_env`, and residuals in `_wire_main_pipeline`) migrate onto capabilities or position defaults, mechanically gated.

**C0/C1/C2 are deterministic pure functions inside `compile_scope`**, covered by the spec-hash byte-stability guard (same declaration + same registry → identical hash, predicates included). The `CAPABILITY` slot is the only compile-time-resolved slot — every other slot stays late-binding at assembly; a mechanical gate anchors that asymmetry.

## Considered Options

- **Framework-hardcoded default capability set** (the v1 draft's `root/non-root default [subagents]`) — rejected: the framework would know capability names, violating plugin self-containment; the same zero-config behavior is expressed as the `subagents` auto-apply predicate.
- **Whole-list replacement semantics for `capabilities:`** (mirroring `tools:` wholesale list replacement) — rejected: with an auto face, no single agent declaration statically reads as "the full set"; a list form is ambiguous between "enable these" and "replace all", and the veto/vetoed distinction disappears. Override mapping keeps one authority (the bill).
- **Source-gated auto-apply** (bundled/project may auto-apply; user/entry_points declaration-only) — rejected: installing a plugin already runs its Python — the trust boundary is installation, not composition. The silent-apply risk is carried by bill three-state provenance with `registration_source`. Flip condition recorded: real third-party "installed and it went global" complaints.
- **Enablement decided by framework-scanned capability metadata** (capabilities declare static metadata, the compiler interprets) — rejected: the judgment is capability-domain knowledge (topology participation for `subagents`, `use_terminal` for a hypothetical terminal-safety package); a metadata schema would recreate per-capability parsing inside the compiler.
- **Keep runtime tool-registration gates** (the legacy shape: hooks and prompt providers probe `tool_manager.is_registered` at runtime) — rejected: the effective set is known at compile time; runtime probing is the historical accident this decision removes.

## Consequences

- `compile_scope` gains a `registry` parameter (process-singleton; not part of the hash input). V12 (external agent with a non-empty explicit `capabilities` block → boot error) and V13 (unregistered capability reference → boot error, one cycle earlier than slot late-binding) join the validator; V6 stays in the validator as a skeleton-integrity rule (the `task` name is coupled to broker/session-tree/invocation machinery and does not generalize to third-party dispatch tools) with `subagents`' bind as a second, richer-error check.
- `ToolSupplement`, `tool_supplements`, `_derived_entries`, the compiler experience special cases, `TodoAwareSystemPromptProvider` / `AgentCommunicationSystemPromptProvider` runtime gates, and `PoolRuntimeDeps.todo_store` / `.communication` typed fields all die; pool supply converges onto one `capability_supply` mapping.
- The system prompt has two fixed capability-section anchors: `HEAD` (default; after fork context, before core memory) and `TAIL` (the final system-prompt block). Sections are ordered by declared `order` within each anchor, and every active section must produce exactly one provider. Placement selects one of these fixed anchors rather than an arbitrary insertion point, preserving deterministic prompt geometry and KV-cache behavior; volatile reference catalogs such as Skills use `TAIL`.
- Zero-config behavior is an explicit split-brain anchor: an empty declaration must compile byte-identically to the pre-migration compiler output, and each migrated capability's predicate output must equal the legacy "does this agent get it" judgment.
- Implementation specification (five-phase protocol, migration tables per bundled capability, waves W1-W6 with deletion ledgers, acceptance criteria): `docs/design/capability-bundles/SPEC.md`. Implemented 2026-08-28 (W1-W6 complete; five bundled capabilities migrated facet-equal per SPEC §14; plugin author guide: `docs/design/capability-bundles/AUTHOR-GUIDE.md`).
- The Experience and Skills vertical slices (full feature ownership under `plugins/defaults/capabilities/{experience,skills}/`, the settled Skills disk-assignment and resolver semantics above) are executed by `ARCHITECTURE-MIGRATION-PLAN.md` (§10–§11, work packages D1/D2). That plan refines this ADR; it does not replace it, and no parallel ADR is created for it.
