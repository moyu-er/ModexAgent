# ADR-0049: ACP Agent-Server Surface for Editor Integration

## Context

ModexAgent needs to be drivable by code editors (Zed, JetBrains) through the **Agent Client Protocol (ACP)** — the open JSON-RPC-over-stdio standard for editor ↔ coding-agent communication (analogous to LSP for language servers). Reference projects (under `references/`, outside the repo) that implement it as an agent-side server: `kimi-code` (`packages/acp-server`, TS), `opencode` (`src/acp/`), `claude-code` (`src/services/acp/`), `deepseek-harness` (`packages/acp/`), and `hermes-agent` (`acp_adapter/`, Python, the closest prior art). The open questions were: (a) which surface in ModexAgent hosts the adapter, (b) which SDK and version policy, (c) how the ACP permission/mode model maps onto the framework's suspend/resume approval and dual-class sandbox permission model, (d) what process topology (subprocess vs. resident bot_service).

## Decision

**ACP is a new framework surface `src/modex_agent/acp/` (business-agnostic protocol mapping) plus a thin business entry `modexbot acp` in `examples/bot_project/`, and it does NOT enter the `@register` channel registry.** The channel registry serves the *resident* bot_service (WebUI/IM long connections, FanIn, ChannelRouter); ACP's process model is the *editor-spawned stdio subprocess*. These are non-isomorphic lifecycles — embedding ACP into the resident service would require a stdio→resident bridge, and would violate ACP's mainstream local-subprocess usage. The two planes coexist (a `modexbot acp` process and a resident bot_service hold separate pool instances; sharing one is a separate future ADR over WS transport, not this one).

**SDK: official Python `agent-client-protocol` (PyPI), pinned to an exact version** (`agent-client-protocol==0.12.1` at authoring time), declared as an optional extra `acp`. It ships Pydantic wire models, the `run_agent` stdio entry, and a Windows-specific stdio transport. Rationale for pinning: the SDK is pre-1.0 and its agent-side surface has drifted across 0.x releases (hermes pins `==0.9.0`; the current 0.12.x moved schema types to `acp.schema` and changed the permission-outcome shape). Version upgrades are a deliberate chore, gated by re-running the e2e verification.

**One sanctioned Protocol exception (type-safety rule 7).** The SDK's agent interface is `acp.Agent`, a `Protocol` — ModexAgent implements it by **structural subtyping** (define the method set, do not inherit). This is the only Protocol in framework code, and it is confined to the SDK boundary in `acp/server.py` — the same tolerated pattern as `agents/external/` embedding SDK-bounded harness code. All *internal* seams (`acp/types.py`, `acp/events_map.py`, `acp/backend.py`, `acp/scripted.py`) remain ABCs and Pydantic models per rules 4/7/10–16; `acp.schema` types do not leak past `server.py`/`entry.py`/`events_map.py`.

**Event and approval projection reuse the canonical seams, never a third branch (convergence rule 15).** Streaming output projects through `TurnEvent` (the seam shared by the external-agent harness and WebUI) into `session/update` via a pure `events_map.py`; it does not add an ACP-specific event type. Approval rides the existing suspend/resume loop as one permission round-trip (`PermissionPrompt` → `PermissionChoice`, once-only options; the ACP layer models no batches — ADR-0011 batch atomicity belongs to the framework's approval transaction inside the pool's resume loop). Production approvals are routed by their **real source session**: a child-session approval view rides the emitter hub's parent-chain resolver to the open editor root while the decision is submitted back to the source session that owns the suspended turn. There is **no** `ApprovalBridge`/batch-model mapping layer and no `always` session-remember kind (deleted with the earlier spike-era draft; `PermissionPrompt` carries no turn id — the server prefixes the wire card id per prompt). Session identity maps ACP `sessionId` ↔ framework `SessionInfo` through a typed origin marker on session metadata (the `ExternalSessionMapStore` pattern per ADR-0022/0027 is not used).

**Out of scope for this phase.** Reverse-RPC filesystem (`fs/*`) and terminal (`terminal/*`), multimodal prompt input and attachment delivery, model switching, plan/auto modes, always approvals, elicitation, session fork/resume/close extensions are not implemented or advertised. File/exec remain local and surface through tool updates. The first valid new/load cwd binds the process; configuration or `--pool` selects its fixed pool. External-main capability acceptance is deferred. Unsupported requests fail explicitly instead of receiving success from placeholder implementations.

## Considered Options

- **ACP as a `@register("acp")` channel in the resident bot_service** — rejected: lifecycle mismatch (resident service vs. editor-spawned subprocess) and it would need a stdio→resident bridge; the registry's `FanInInputAdapter`/`ChannelRouterOutputAdapter` model has no place for a synchronous request/response `session/prompt` contract.
- **Vendor the SDK or hand-roll the wire protocol** — rejected: the official SDK already carries the Windows stdio transport, the Pydantic schema, and version negotiation; hand-rolling re-owns a drift-prone wire surface. Pinning plus a mapping-layer firewall contains the drift.
- **Implement `fs/*` / `terminal/*` reverse RPCs** — rejected for v1: they duplicate the workspace sandbox's authority and would let the editor bypass scope-declared resources; the loss (unsaved-buffer reads) is acceptable and reversible.
- **`Protocol` subclassing instead of structural subtyping** — rejected: inheriting `acp.Agent` would couple every method signature to the SDK and make the Protocol visible across the module; structural subtyping keeps the Protocol at one boundary line.

## Consequences

- Framework package `src/modex_agent/acp/` exposes SDK-free `AcpSessionBackend` / `AcpSessionHandle` / `AcpInteraction`, typed permission values and pure event/history mappers. The SDK receives a `ModexAcpAgent` instance and supplies its client through `on_connect`. The entry owns one shielded cleanup task: agent drain precedes backend close, cancellation waits for settlement, and transport/cleanup failures remain observable. Shell discovery probes detach stdin and suppress windows so they cannot consume the editor's protocol pipe.
- Bot entry `modexbot acp` binds the first protocol cwd to one IDE project and a fixed native-main pool through `BotAssemblyRoots`; execution consumes the existing `begin_request`/`run_input` contract. `BotTranscriptEmitter` owns shared recording while WebUI and ACP own distinct projections. Workspace-routed transcript storage has an explicit adapter contract and uses the existing release path. ACP also enters the existing external-process lifecycle, without starting resident IM/WebUI loops or introducing another process manager. Existing channel behavior remains unchanged.
- **Single-project refinement (merged from the design baseline):** one ACP process binds one IDE project workspace and one selected pool — no workspace/pool switching, no multi-project support in one process; `initialize` never boots, and a `cwd` mismatch after binding is a typed `project-mismatch`. Full contract: `docs/design/acp-adapter/DESIGN.md` + `PLAN.md`.
- The optional `acp` extra must not be imported by the default install path (import-light boundary, mirroring the capability-package rule in ADR-0047).
- Windows is a first class target. Real-stdio production assembly with a scripted provider covers relative-path tools, once approval, cancellation, unsupported commands and FILE/SQLite restart-load. Framework and bot default full suites pass; counts and exclusions are recorded in PLAN.md. IDE/manual and live-model acceptance remain open.
- Native subagents default to no human approval (unchanged); subagent-approval coverage in tests uses an explicit approval-gated test child, not a default flip.
