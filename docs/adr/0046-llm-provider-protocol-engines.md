# Rebuild the LLM provider system: one provider, protocol engines, event-stream primitive

**Status**: Accepted
**Date**: 2026-08-25

## Context

The framework's two legacy provider implementations (one on the native OpenAI SDK, one on litellm) each hand-roll the same streaming loop, error handling, and usage extraction; both are weak in different ways. Header passthrough has no config path at all (the OpenAI-SDK provider accepts `extra_headers` but nothing feeds it; the litellm provider has no such parameter). Anthropic support exists only as a litellm string-routing convention (`anthropic/` model prefix) with no native Messages API. The OpenAI Responses API is unsupported. `_extract_delta` in the litellm provider probes responses with `hasattr`/`getattr` — a violation of the project's own type-safety rules. Reasoning content rides on `ChatMessage.model_extra`, which cannot carry structured replay state.

Two reference systems were studied in depth: DeepSeek Harness (dsh) and opencode's `@opencode-ai/llm`. Both converge on the same core: **the event stream is the only streaming primitive** (generate = collect(stream)), the canonical message model is a typed content-block union where reasoning and media are first-class parts, storage format ≠ wire format, and per-protocol translation lives in dedicated protocol modules that are structurally self-similar. opencode additionally decomposes a provider route into four orthogonal axes (Protocol / Endpoint / Auth / Framing), which lets a new OpenAI-compatible vendor be a 5–15 line configuration instead of a code clone.

## Decision

Rebuild as **one concrete provider + three protocol engines + a provider-neutral event stream**, replacing both existing providers:

1. **Layering.** `LLMProvider` remains the public ABC with an unchanged `chat_stream` signature (86 call sites, 40+ mocks untouched). `stream(request) -> AsyncIterator[LLMStreamEvent]` is the single streaming primitive; `chat_stream` is a concrete fold of the event stream with delta callbacks into `LLMResponse`. One concrete `HTTPStreamProvider` owns transport (httpx.AsyncClient, SSE framing, idle watchdog, HTTP error classification). `LLMProtocol` engines (`openai_compat`, `openai_responses`, `anthropic`) own request-body building and stream-to-event translation, each with its own private wire structs. `provider.py` contains zero `if format ==` branches; engines are stateless across requests (per-request state lives in the translate generator's closure). Refined 2026-08-26: model names pass through the call path VERBATIM — no routing-prefix stripping, inference, or validation anywhere (a stale `openai/`/`anthropic/` prefix reaches the API as part of the model name; the API's "model not found" is the natural error) — and the factory (`create_llm_provider`) resolves the final request URL (`endpoint_url` verbatim when set, else the engine's `url()` join on the normalized `base_url`), handing the provider one resolved `url` that it requests unchanged; the provider holds zero URL-construction knowledge. Refined 2026-08-26 (ABC convergence): the migration's two-tier ABC — an event-stream tier introduced above the legacy callback tier — collapsed once the cutover landed. `LLMProvider` itself is now the event-stream ABC (abstract `stream()` + `get_default_model()`; concrete `chat_stream()` fold and `chat()` with one internal retry; no public retry entry point), `HTTPStreamProvider` extends it directly, and response-level implementations (cassette record/replay, delegation proxies, scripted test providers) subclass `CallbackStreamProvider`, whose concrete `stream()` bridges `chat_stream()` into the event stream. The intermediate tier was the migration stepping stone, not the end state.

2. **Message model.** `ChatMessage` is promoted to the canonical message model: reasoning state becomes four declared fields (`reasoning_content` promoted from `model_extra` — same persisted key, zero migration; plus `reasoning_signature`, `reasoning_item_id`, `reasoning_encrypted_content`, all nullable, landing in the existing `message_json` residual column / JSONL with no schema change). No per-protocol intermediate model above the wire structs: the canonical model is shared by storage, memory, governance, and requests; protocol engines lower it per format. A neutral block-union model (the opencode/dsh route) was rejected because our `ChatMessage` is already the de-facto canonical model with 336 call sites and its own storage format.

3. **Reasoning.** All three protocols support reasoning display in V1. DeepSeek-style `reasoning_content` passback stays (declared field, replayed on assistant tool-call turns). Anthropic extended thinking is sent (`thinking: {enabled, budget_tokens}` mapped from `ReasoningEffort` with a budget table overridable via `extra_body`) and its `signature` replayed (`reasoning_signature`). OpenAI Responses reasoning items replay via the full item carrying `encrypted_content` by default (store=false — the default flipped 2026-08-27 per flip condition (c): third-party Responses endpoints such as kimi reject `store=true`, and the opencode reference defaults to store=false on its native route); `item_reference` replay sits behind the store=true switch. A store=false replay without `encrypted_content` drops the reasoning item with an ERROR log — the API rejects a bare replay item (opencode filter semantics). `LLMResponse` carries the same replay fields so the ReAct LLM node can persist them onto the assistant message through the existing `build_assistant_message` seam.

4. **Sampling parameters** travel in the `LLMRequest` envelope (`temperature=0.7`, `top_p=0.95`, `reasoning_effort=NONE` meaning "omit", `max_output_tokens` from model config, `stop=None`), merged call-site > provider config > built-in default. HTTP headers carry only auth and user-configured passthrough (case-insensitively merged, user wins — overriding `Authorization` is a documented feature, not a bug).

5. **Provider boundary: fail loud.** Protocol engines validate structure and raise typed errors; they never silently repair history (orphan tool messages, dangling tool_use). Content repair and history hygiene belong to the governance layer, which is a separate parallel workstream. Internal-to-wire role normalization (`compact`→`assistant`, `system_reminder`/`agent`→`user` via `normalize_agent_messages_for_llm`) stays in the pre-LLM context-assembly step where it lives today — protocol-agnostic, operating on the in-memory context copy; protocol engines accept only the four standard roles and degrade anything else to the nearest standard role with an ERROR log, so a path that bypasses the pre-step survives locally instead of sending an invalid role to a vendor. Per-format field mapping (system→instructions vs top-level system, TOOL→function_call_output vs tool_result block, which fields exist at all) is the body of each engine's `build_body` — explicit construction from the canonical model, never a filter over a serialized dict, so governance-internal fields cannot leak onto the wire by construction. Unsupported content-part types and unrecognizable roles are **degraded, not raised**: log at ERROR and skip/merge (part skipped, role merged to the nearest standard role) — a long-running session must survive one foreign block in deep history, and the ERROR log keeps the defect discoverable. This is the same degradation philosophy as mid-stream errors preserving partial content. Structural pairing violations (orphan tool messages, dangling tool_use) still raise typed errors — the dividing line is "does skipping it leave the remaining message sequence legal": a skipped content part degrades one message; a skipped pairing record corrupts the sequence. The one surviving "quirk parsing" in a protocol engine is `<think>`-tag extraction, because it parses provider *output*, which governance (a request-time concern) cannot reach.

6. **Transport discipline.** `httpx.Timeout(connect≈10s, read=None, write≈30s, pool≈10s)` at construction only; `asyncio.wait_for(anext)` is the only idle mechanism (no double watchdog). The assembler enforces a terminal-event invariant: a stream that ends without `Finish`/`StreamFailure` becomes an error response preserving partial content. Tool-call accumulation keys on the provider's stream key (block `index` or `item_id`), never on `call_id`; authoritative final arguments come from done-events where the protocol provides them. Usage is a typed `TokenUsage` with disjoint counts and a computed `total_tokens`. Provider instances are cached per config (per-turn model switching must never construct a provider + HTTP client per turn).

7. **Deletion.** The legacy SDK provider classes, the shared provider-utility directory, and the streaming tool-call accumulator are deleted once evals run green on the new system (executed in the 2026-08-26 cleanup); litellm leaves the import graph. The `LLMProtocol` ABC is the long-tail extension point — a future Gemini engine is a new engine, not a revived legacy provider.

## Considered Options

- **Three provider subclasses vs one provider + strategy engines.** Subclasses would re-create the protocol ABC inside the class hierarchy while breaking the "one concrete provider" testing story. Strategy split kept.
- **Neutral `LLMRequestMessage` block-union above ChatMessage (opencode route).** Purer canonical model, but adds a model + a translation layer; opencode needs two layers only because its session model is legacy AI-SDK-shaped, while our ChatMessage is ours to evolve. ChatMessage-as-canonical kept; flip condition recorded below.
- **Reasoning replay as a bundle (`reasoning_replay: ReasoningReplay | None`) or a provider-metadata dict.** Flat declared fields chosen: 1:1 with wire concepts, zero storage migration, and we refuse open dicts on principle. The bundle wins only if a second family of per-provider replay fields (e.g. Gemini thought signatures) appears.
- **dsh-style public StreamChunk protocol + adapter registry.** Rejected: our callback + `LLMResponse` contract is load-bearing for 40+ mocks and the trace cassette; an enum + factory suffices for three known formats.
- **Repair orphan tool chains inside the provider (drop + loud log).** Rejected in favor of fail-loud + governance ownership: silent repair hides compaction data-loss bugs.

## Consequences

- The trace cassette moves to content-addressing on the serialized `LLMRequest` (kwargs hashing retires); recorded cassettes must be re-recorded at cutover — response schema changes (`TokenUsage`) also invalidate old recordings. This is planned, not accidental.
- The legacy OpenAI-SDK provider's `_sanitize_api_messages` field whitelist dies entirely: protocol engines build wire bodies by explicit construction, so governance-internal fields (`token_count`, `content_format`, …) never appear by construction. Its one non-trivial behavior — replaying `reasoning_content` on assistant tool-call turns only (the DeepSeek thinking-mode rule) — moves into the `openai_compat` protocol engine's message lowering, alongside Anthropic's thinking+signature replay and Responses' item_reference replay. Replay rules are per-protocol wire quirks and belong where the wire format is known; the governance layer stays protocol-agnostic (it compresses/repairs a faithful context copy and never strips reasoning state), and persisted history always keeps reasoning intact — the "send or not" decision happens only at lowering time.
- `build_assistant_message` and the ReAct LLM node gain the replay-field pass-through; `chat_span_hook` usage reads become attribute access (it already reads the semantic key names — the typed model is the natural endpoint of an existing migration).
- Multimodal V1 is images only (`ImageUrlPart` with data URLs, lowered by all three engines); a `FilePart` slot is reserved in the content-part union but unused. Document-as-file and Files-API upload paths are deferred.
- Flip conditions: (a) if the memory layer later reshapes the message model wholesale, re-evaluate a neutral canonical layer; (b) if a second per-provider replay-field family appears, re-evaluate bundling; (c) ~~if privacy-sensitive deployments dominate, flip the Responses `store` default to `false`~~ — flipped 2026-08-27: third-party Responses endpoints (kimi and similar coding endpoints) reject `store=true` outright, so store=false + `encrypted_content` replay is the default; `store=true` remains a per-provider opt-in (`responses_store: true`).
