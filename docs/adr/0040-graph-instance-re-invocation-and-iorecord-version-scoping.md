# Graph Instance Re-invocation via Version Chain + IORecord Version-scoping

## Context

The graph scheduling subsystem (`modex_graph` + `GraphOrchestrator`) models graph execution as a two-level version chain: `GraphInstanceStore` holds per-instance versions, `NodeStateStore` holds per-node versions. `GraphIORecordStore` holds input/output records. The original design assumed one **Graph Instance** per spec execution — `runGraph` always created a new instance. The WebUI's `GraphConversation` component treated each run as a chat bubble, creating a new instance every time the user sent input.

This created an information-architecture mismatch: users expected "send input to a graph" to work like a conversation (continue the same instance), but the system created a new instance each time. The WebUI showed chat bubbles instead of a topology view, and there was no way to continue a completed/failed instance with new input.

## Decision

**Graph Instance is reusable.** A completed/failed instance can be re-invoked by calling `GraphInstanceStore.begin_invocation(gid)`, which creates a new version (N+1) on the same `graph_instance_id`. The new version executes the graph from `entry_node` as a fresh execution. The old version's records (graph + node) remain as history; the version number ordering (`ORDER BY version DESC LIMIT 1`) naturally makes `load_latest` return the new version — no explicit soft-delete field is needed.

Two convergent changes:

1. **`bootstrap` removes the `has_any_invocation` gate for re-invocation.** The current `bootstrap` returns `[entry_node]` only when there are NO prior node invocation records (`has_any_invocation is False`). For a completed instance being re-invoked, prior COMPLETED node records exist → `has_any_invocation is True` → bootstrap returns `[]` (empty seeds) → `ParallelScheduler` does not execute. The fix: when seeds is empty (no CRASHED/RUNNING nodes, no PENDING delivers), bootstrap checks the instance status — if RUNNING (`begin_invocation` just set it, meaning this is a re-invocation), return `[entry_node]` unconditionally (the `has_any_invocation` gate is removed for this path); if terminal (COMPLETED/FAILED/CRASHED, meaning this is a recovery/query), return `[]` (graph is done); if the instance store returns None (Null store), fall back to the `has_any_invocation` check. The node's existing version chain handles the rest: `NodeStateStore.begin_invocation(node_id)` creates a new version (`MAX(version) + 1`), the old COMPLETED record is implicitly superseded by the higher version number, and `load_latest` returns the new RUNNING record. The version number ordering IS the superseding mechanism, uniformly at both graph and node layers — no `superseded` field is needed.

2. **`GraphIORecord` version-scoped.** `GraphIORecord` gains a `version: int` field aligned with `GraphMetadata.version`. `run_instance` creates a new `GraphIORecord` on each `begin_invocation` (not just on `create_instance`). `get_by_instance` is replaced by `list_by_instance` (returns all versions) or `get_latest_by_instance` (returns the active version). This makes each invocation's input/output independently queryable — the "conversation history" of a graph instance.

## Why

The current design's `bootstrap` infers "should we re-execute?" from **node-level** status — the `has_any_invocation` gate returns `[]` for completed instances because prior COMPLETED node records exist, blocking fresh-start. This couples the instance-level re-invocation decision to node-level state, creating the divergence where `LinearScheduler` happens to work (entry_node fallback) but `ParallelScheduler` silently fails (no fallback). The fix removes the `has_any_invocation` gate for the re-invocation path: when seeds is empty and the instance status is RUNNING (set by `begin_invocation` just before the scheduler runs), bootstrap returns `[entry_node]` — prior COMPLETED node records do NOT block re-execution. For recovery (terminal status), bootstrap still returns `[]` (graph is done). For Null stores (no instance metadata), the `has_any_invocation` fallback remains. The node's existing version chain (`begin_invocation` creates `MAX(version)+1`, old records implicitly superseded by version ordering) handles per-node re-execution without any schema change.

## Considered Options

- **`NodeStateStore.clear()` on re-invocation.** Deletes all node states for the instance before re-execution. Simpler (no schema change), but destroys node-level history (timeline, crashed node records). Rejected because the WebUI's instance detail view shows per-invocation node execution traces, and clearing them would make historical debugging impossible. The version chain already preserves history implicitly — old versions stay in the table, `load_latest` returns the newest.

- **Version-scoped `NodeStateStore` (add `instance_version` column).** Node states keyed by `(graph_instance_id, node_id, node_version, instance_version)`. Queries filter by instance version. Rejected because it requires every `NodeStateStore` query to carry an `instance_version` parameter — a pervasive API change across `bootstrap`, `Node.run()`, `persistence_coordinator`, and all three store implementations. The existing version chain (`MAX(version)+1`) already provides isolation — re-invocation creates new versions that naturally supersede old ones via ordering.

- **`superseded` field on `graph_instances` and `node_states`.** An explicit boolean column set to 1 when a new version supersedes the old. Queries filter `WHERE superseded = 0`. **Deferred** — the version number ordering already provides the same semantics for correctness (`load_latest` returns `ORDER BY version DESC LIMIT 1`, naturally the newest; `begin_invocation`'s `MAX(version)` is O(log n) via existing B-tree index). The `superseded` field would not reduce `begin_invocation`'s `MAX(version)` cost (version calculation must scan all versions to stay continuous). Its only benefit is replacing `load_by_status`'s group-by-MAX subquery with a simple `WHERE superseded = 0` filter, plus potential partial-index optimization. At current scale (tens to hundreds of versions per instance), this is not a performance concern. Revisit when version chains grow to thousands per instance; at that point add `superseded` + partial index `WHERE superseded = 0` on both tables as a pure query optimization, without changing any API or logic.

- **`bootstrap` entry_node fallback in `ParallelScheduler`.** Mirror `LinearScheduler`'s `seeds[0] if seeds else entry_node` fallback. Rejected because it treats the symptom (empty seeds) not the cause (bootstrap not returning `[entry_node]` for re-invocation). The correct fix is removing the `has_any_invocation` gate so bootstrap returns `[entry_node]` directly.

## Consequences

- `bootstrap` no longer applies the `has_any_invocation` gate for the re-invocation path — when seeds is empty and instance status is RUNNING, it returns `[entry_node]` unconditionally. For terminal status (recovery), it returns `[]`. For Null stores (no instance metadata), the `has_any_invocation` fallback remains. A re-invocation (RUNNING status, prior COMPLETED node records) and a fresh start (no prior records, Null store) both return `[entry_node]`; a completed instance on a real store returns `[]` (recovery, graph is done).
- `LinearScheduler`'s `seeds[0] if seeds else entry_node` fallback (line 85) becomes redundant for the re-invocation case (bootstrap now returns `[entry_node]`). It remains as a safety net.
- The `GraphIORecordStore` ABC gains `list_by_instance` as the primary query (already exists); `get_by_instance` (returns single, `LIMIT 1`) is deprecated or removed.
- No schema changes to `graph_instances` or `node_states` — the existing version chain (`MAX(version)+1`, `ORDER BY version DESC LIMIT 1`) is the superseding mechanism, uniformly at both layers.
- The WebUI's `GraphConversation` component is replaced by a spec-detail view (topology + instance list + new-instance composer) and an instance-detail view (execution viewer + continue-invocation composer). The old `runGraph`/`getRuns` API names are renamed to `invokeInstance`/`getInvocations` to align with the **Graph Invocation** term.

## Deferred (not in this ADR's scope)

The following items are explicitly **not done now** but recorded here to prevent design and implementation drift:

- **`superseded` field as query optimization.** A `superseded INTEGER NOT NULL DEFAULT 0` column on `graph_instances` and `node_states`, set to 1 by `begin_invocation` on the prior version. All "load active" queries filter `WHERE superseded = 0`. Benefits: (1) `load_by_status` replaces group-by-MAX subquery with simple filter; (2) partial index `WHERE superseded = 0` makes active-version lookup O(1) instead of O(log n). Not needed now — current scale (tens to hundreds of versions) has no performance issue. Revisit when version chains reach thousands per instance. Note: `begin_invocation`'s `MAX(version)` must still scan all versions (filtered or not) to keep version numbers continuous — `superseded` does not help that query.

- **Running-state dirty data cleanup.** When the process is killed mid-execution, the instance status stays `running` but no execution is active. A periodic cleanup task should mark stale `running` instances (heartbeat timeout) as `crashed`, making them re-invokable. Not addressed now — current re-invocation only handles `completed`/`failed`/`crashed` statuses. The `running` status blocks re-invocation (the status check rejects it). Future design: heartbeat + timeout + auto-mark-crashed.

- **`rebuild_main_state` on re-invocation.** `bootstrap` step 1 calls `coordinator.rebuild_main_state()` which restores `ctx.state` from the newest COMPLETED node record's `state_json`. On re-invocation, this restores the prior invocation's final state. `run_instance` creates a fresh state before `bootstrap` runs, but `bootstrap` overwrites it. Whether re-invocation should carry prior state forward or start fresh is a semantic decision deferred to implementation time — the current code path creates fresh state in `run_instance`, and `bootstrap`'s `rebuild_main_state` may need to be skipped (or not) for re-invocations. This is an implementation detail to verify, not a separate ADR.
